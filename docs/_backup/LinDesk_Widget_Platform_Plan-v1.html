LinDesk 组件系统打磨方案

定位：组件系统是项目差异化灵魂 核心开发者：AI（无 SDK、无设计令牌、视觉自由） 更新：2026-10-12 性质：方案任务书（供 antigravity / 开发者排期执行）

1. 背景与定位

LinDesk 的差异化价值在于 HTML 组件系统：任何 HTML/CSS/JS 内容都能成为桌面组件。CEF OSR 渲染、消息桥、交互路由已全部实现，本方案把组件系统从"能用的容器"打磨成"可生长的平台"。

核心开发者是 AI 而不是人（已拍板）：SDK、TS 类型、API 文档站点等"人向"工具一律不做。平台的三项职责是——

  • 给 AI 清晰的规则：协议规范极简固定、示例组件可参考；
  • 给 AI 及时的反馈：校验器报错、运行时日志/异常可导出、意图可保留；
  • 给 AI 的产物安全兜底：权限最小化、危险代码拦截、资源限制。

视觉自由（已拍板）：不做设计令牌、不做视觉规范强制。组件长什么样由作者和用户决定，平台只管功能、安全与迭代闭环。

2. 前置地基：CEF 四项技术缺口（P0，先行）

打磨建立在渲染栈完整之上。以下四项是当前 CEF 迁移遗留的功能缺口，必须先补齐，否则作者层（运行时反馈）与运行层（权限沙箱）无从谈起。

缺口现状（代码依据）影响实现要点
IME 候选窗口CefOsrBrowserInstance.cpp:487-513 有 ImeCommitText / ImeSetComposition / ImeCancelComposition，但 OnIMECandidateCountToQuery / OnIMECompositionRangeChanged 等回调未实现中文输入候选框/组合框不显示，输入体验不完整补 CefOsrRenderHandler 的 IME 回调，参考 cefclient 的 osr_ime_handler_win.cpp
本地资源 scheme组件以 file:// 直载（WidgetManager.cpp:737/809/1179），无自定义 scheme、无 GetResourceHandler跨目录资源、组件内 fetch 本地数据受 Chromium 同源/CORS 限制，现在"能用但脆"实现 linwidget:// 自定义 scheme，按组件包目录映射；CSP 头随 scheme 响应统一注入（不单独立项）
console 捕获OnConsoleMessage 无实现，调试面板日志查看器无组件 console 来源AI 无法看到组件运行时输出，迭代闭环断一环CefDisplayHandler::OnConsoleMessage 转发到调试面板日志查看器

3. 作者层：AI 开发闭环

AI 不需要 SDK，需要"规范 + 示例 + 校验器 + 反馈"。作者层的五个环节构成闭环：AI 读规范与示例 → 生成组件包 → 校验器报错 → AI 按错误修 → 安装运行 → 诊断导出再迭代。

3.1 协议规范（定稿）

  • 以现有 handleRuntimeMessage（WidgetManager.cpp:1906）已支持的消息面为准，收敛固化，不新增无谓类型：geometry、settings、system_info、storage、实例管理（create/list/close）、error 等；
  • 字段命名统一 snake_case；每类消息配一个请求/响应 JSON 示例；
  • 错误码固定 3 个：OK / DENIED（权限拒绝）/ INVALID（参数或格式错误），拒绝与失败必须显式返回错误码而非静默；
  • 文档短到能整段放入 AI 上下文，作为组件生成的输入素材。

3.2 示例组件仓库

  • GitHub 开源：官方最小组件模板 + 3 个完整参考实现（Clock / Notes / Todo）；
  • 既是 AI 生成的 few-shot 素材，也是人工调试的对照物；
  • 仓库同时承载组件索引（见第 4 节）。

3.3 组件校验器

  • 安装时 lint：manifest 字段完整性、权限是否声明、HTML/JS 语法；
  • 输出结构化错误清单（位置 + 原因 + 修法），可直接反馈给 AI 迭代；
  • 危险模式扫描分级：error 确定有害（eval + 远程代码执行、远程脚本注入）；warning 可疑（内联事件、超大包、未声明权限却出现外部请求）；
  • 与权限模型联动（防误伤）：外部请求类代码只有在"manifest 未声明对应权限"时才判为错误——Weather 组件合法请求天气 API 不因出现外联 URL 被拦。

3.4 运行时反馈与诊断包

  • console / 未捕获异常 / 网络请求记录转发到调试面板日志查看器（依赖 2.3 缺口）；
  • 调试面板提供一键导出诊断包：组件 manifest + 运行日志 + 异常 + 最近错误，格式化为可直接粘贴给 AI 的文本；
  • 脱敏约束：诊断包只含组件自身数据，不包含用户桌面其他信息。

3.5 意图保留

  • manifest 记录生成意图（原始需求描述 + AI 引擎/版本）；
  • 组件出问题时，把"旧包 + 意图 + 新需求 + 诊断包"四件套喂给 AI，做增量修复而非推倒重写，成功率更高、结果更稳定。

3.6 生成入口（远期可选，不做承诺）

  • 主路径（现在就用）：用户在任意 AI 工具（Cursor / 豆包等）里按规范 + 模板生成组件包，LinDesk 负责校验与安装；
  • 远期可选：调试面板内"描述式生成"（调大模型 API 返回组件包），仅作探索，不作为本方案交付项。

4. 市场层：组件发现与更新

复用此前已完成设计的 GitHub 更新方案思路（客户端请求 GitHub Releases API + gh CLI 发布 + digest 免手算）同构实现，不引入新基建。

能力设计要点
组件索引GitHub 仓库根目录 index.json：组件 id / 名称 / 简介 / 图标 / 最新版本 / 包下载 URL与组件示例仓库合并维护，版本号由发布流程统一管理（避免 AI 乱写版本）
在线安装 / 卸载拉取 index.json → 展示列表 → 下载 .lw 组件包 → SHA-256 校验 → 解压到组件目录 → 注册校验失败拒绝安装并提示原因；卸载保留用户数据（storage 按组件隔离，卸载仅移除代码）
组件更新启动时（或手动）对比已装版本与索引最新版，提示一键更新复用 UpdateChecker / compareVersions 数字语义；更新前备份旧包可回滚
离线降级GitHub 不可达时组件照常运行仅不提示更新；安装/更新按钮置灰并说明原因，不做静默失败
来源信任哈希校验 + 来源白名单（官方仓库固定）第三方索引暂不支持，避免供应链风险

5. 运行层：权限、推送、生命周期、沙箱

5.1 权限模型（收敛，避免过度设计）

  • 保持三类为主：network（外联请求）/ storage（组件数据读写）/ desktop（桌面集成：拖放、文件、快捷键预留）；可选扩展 clipboard；
  • 不做存储读写分离：拆"读/写"两个权限增加协议复杂度、收益低，组件作者与 AI 都更难理解；
  • 安装时最小化授予：只授予 manifest 声明且校验器通过的权限。

5.2 运行时申请流

  • 组件首次调用未授权权限时，平台弹窗询问；请求挂起等待用户决策，避免组件无限重试；
  • 拒绝后该 API 返回 DENIED 错误码（协议可见，AI 能据此修）；
  • 同组件同权限记住选择，不重复弹窗；用户可在调试面板权限页随时撤销。

5.3 订阅-推送

  • system_info 在现有 request/response 基础上增加 subscribe / unsubscribe；
  • 推送按 1s 节流，组件挂起时不推送、恢复后补一帧；
  • 组件必须显式取消订阅，避免泄漏（组件销毁时平台强制清理）。

5.4 生命周期（定义要克制）

  • 挂起条件：窗口最小化 / 组件被显式隐藏时暂停渲染帧（OSR WasHidden）；不做窗口遮挡检测（桌面层级复杂、收益低）；
  • 内存压力时按 LRU 卸载挂起组件的 OSR 实例；恢复时重建实例 + 加载组件包 + 从 storage 恢复状态（成本明确：一次实例创建 + reload）；
  • 状态恢复依赖 layout.json（geometry，已有）与 storage（组件数据，已持久化）——不再设计额外的数据快照机制。

5.5 沙箱

  • 网络：OnBeforeResourceLoad 按 5.1 权限放行/拦截（补 2.4 缺口）；
  • CSP：随 linwidget:// scheme 响应统一注入，锁定远程脚本/外联字体等（随 2.2 缺口一并实现，不单独立项）；
  • 资源配额：组件存储上限（如 16MB），超限 API 返回 INVALID 并提示。

6. 体验层：设置、状态、交互（视觉自由）

能力设计说明
设置 UImanifest 声明 settingsSchema（开关/滑块/下拉/颜色），平台自动渲染设置对话框；与组件自带 settings.html 并存schema 是新组件推荐方式；既有组件（如 Notes 的 settings.html）保留，不做强制迁移，避免破坏性改动
状态恢复重启恢复组件位置（layout.json）与数据（storage）两项机制已具备，本方案不新增工作，仅在打磨时验证覆盖度
交互拖拽吸附网格、Shift 锁定、右键层级菜单、多选批量移动在现有 geometry 同步（WidgetGeometryChanged）基础上加交互层
视觉无强制约束作者与用户发挥；平台不注入设计令牌、不限制样式

7. 底层治理（已具备，保留）

  • 崩溃自动恢复：handleBrowserCrashed，60s 内最多 3 次重启，超限停止并提示（WidgetManager.cpp:1355）；
  • 调试面板热重载：单组件 Reload、开发模式 hot reload；
  • 日志与诊断：qWarning/qCritical 记录 + 崩溃原因输出，供诊断包聚合。

8. 壁纸组件（role: wallpaper）

8.1 定位与设计原则

动态壁纸是组件系统内部的特殊组件类型（manifest.role: "wallpaper"），与普通组件共用包规范、CEF OSR 实例、消息桥、权限模型、Canvas 帧合成与注册表/调试面板入口。不做独立运行时，不复刻 WebView2 时代的 LinWallpaperWebViewRuntime。组件系统只有一种组件，role 只区分行为。

8.2 现状盘点（代码依据）

层现状结论
包格式manifest.role 默认 "widget"（LinWidgetTypes.h:24）；launchWidgetInstance 对 role=="wallpaper" 分流（WidgetManager.cpp:483-488，instanceId=wallpaper:{id}）→ startWallpaper格式已定义，运行时待实现
持久化filterWallpapers 按 role 过滤（WidgetManager.cpp:956），壁纸不落 layout.json，走独立壁纸配置（LinWallpapers/Enabled）隔离持久化已设计
绘制ListView::paintEvent 的 hasActiveWallpaper() 分支预留透明遮底（ListView.cpp:1303-1305）；组件帧按嵌入/浮动两模式合成（:1310/:1347）层级挂点已预留
运行时startWallpaper 返回 false + "not yet supported"（WidgetManager.cpp:2172）；activeWallpaperWidget() 返回 nullptr；load/saveWallpaperConfig 空实现唯一要补的核心

8.4 绘制层级（自上而下）

  1. 桌面图标 + 文件名（ListView::paintEvent；浮动模式组件在其上 / 嵌入模式在其下）
  2. 普通组件帧（zOrder 排序合成）
  3. 壁纸组件帧（全屏 OSR 实例，合成最先画）
  4. 透明遮底（壁纸激活时遮系统壁纸底图，ListView.cpp:1303 已预留）
  5. 系统壁纸（LinDesktop m_scaledBackImagePixmap，壁纸停止时恢复）

8.5 消息扩展（协议新增 2 类型）

  • wallpaper_set_source：平台弹文件对话框（C++ 侧）→ 返回本地路径 / 经 scheme 注入 → 组件渲染图片、视频；
  • wallpaper_get_source：恢复时组件读取已选媒体源。

9. 设计决策记录（明确不做）

不做项原因
linwidget SDK / TS 类型 / API 文档站点开发者是 AI，不需要人向的编程拐杖；规范 + 示例 + 校验器已覆盖
设计令牌 / 视觉规范强制用户决策：视觉自由，作者发挥
存储权限读写分离过度设计，协议复杂度上升而收益低
窗口遮挡检测挂起桌面层级复杂，实现成本高、收益低；挂起只由最小化/隐藏触发
settings.html 强制迁移到 schema破坏既有组件；两种方式并存，新组件推荐 schema
组件数据快照机制storage 已持久化，快照是重复设计
内嵌 AI 生成功能承诺主路径是外部 AI 工具生成 + 本地校验安装；内嵌生成仅远期探索
第三方组件索引供应链风险，只信任官方仓库
独立壁纸运行时（LinWallpaperWebViewRuntime 模式）壁纸是组件系统内的 role=wallpaper 特殊组件类型，不复刻独立子系统（见第 8 节）

10. 优先级路线与验收要点

级别内容验收要点

P3组件间通信 + 桌面集成扩展点（拖放/文件/快捷键）组件间通信按来源隔离并需用户授权；拖放/文件 API 走 desktop 权限申请流

11. 风险与依赖

  • 校验器规则质量：与权限模型的联动判定（3.3）是防误伤关键，规则需随真实组件反馈迭代，起步宁严勿松（error 集小、warning 集大）；
  • scheme 是多项能力的共同前置：资源映射、CSP 注入都依赖 2.2，应优先于 P1 市场层完成；
  • GitHub 可达性：组件索引/更新依赖网络，离线降级（4 节）必须随市场层一同交付，避免更新失败打断组件使用；
  • 协议冻结：3.1 定稿后新增消息类型需评审，防止协议膨胀稀释 AI 生成正确率；
  • AI 生成质量下限：由校验器 + 沙箱兜底，不承诺"生成即正确"；坏组件在安装前被拦、运行中被治理。
