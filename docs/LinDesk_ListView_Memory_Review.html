LinDesk 桌面 ListView 内存与健壮性审查报告

审查对象：src/desktop（ListView / ListViewModel / BoxManager / IconCacheManager）· 2026-10-14 · 执行人：anti

一句话结论：Listview 无"new 不 delete"式泄漏（对象生命周期管理整体正确），主要风险是全局图标缓存无上限且失效覆盖不全，长期运行内存单调增长，另有 2 个性能点与 1 个健壮性小问题待修。

级别位置问题影响

2. P1 详解：图标缓存只增不减（重点）

2.1 根因

  • IconCacheManager（src/services/IconCacheManager.cpp）持有两个全局缓存：m_iconCache（QIcon）与 m_imageCache（QImage）。没有任何容量上限、LRU 或自动清理，只有 invalidate* 手动失效与 clear() 全清。
  • 缓存 key 设计：
    • base 图标：{iconKey}|base|{size}（iconKey 含路径，见 DesktopRootItemState.cpp:254）
    • 渲染图：{iconKey}|render|{clampedIconSide}（含尺寸，见 :320）
    • 图片预览：image_preview:{path}|{mtime}|{side}（含 mtime，见 :299）

2.2 三个失效缺口

缺口说明
文件删除不清理ListView::removeItemPathsBatch（ListView.cpp:3229）、LinBox::removeItemState（LinBox.cpp:887）、onFileSystemChanged 删除分支（ListView_Actions.cpp:1154-1173）都只移除 state，不 invalidate 对应 iconKey 缓存，已删除文件的 base/render 缓存永久残留
图片预览 key 天然残留image_preview 含 mtime，文件内容修改产生新 key 后旧 key 没有任何按前缀失效路径（全清只在 viewMode/DPI 变更时触发）
多尺寸叠加每个 clampedIconSide（随 viewMode / 列表模式变化）都新增一份副本，切换越多副本越多

2.3 修复建议

  1. 容量上限 + 淘汰策略：给两个缓存加简单 LRU（如插入顺序 + 访问计数，超上限淘汰最久未用；或设条目上限触发全清），上限建议按桌面规模估算（如 4096 条 QIcon / 4096 条 QImage）。
  2. 删除路径补失效：上述 3 处删除路径补 
    invalidateIconsByPrefix(iconKey + "|base|")
invalidatePixmapsByPrefix(iconKey + "|render|")
invalidatePixmapsByPrefix("image_preview:" + 该文件路径前缀)
  3. image_preview 改失效驱动：去掉 mtime 进 key（避免旧 key 残留），改为文件变更事件（onFileSystemChanged 的 modified 分支）主动 invalidatePixmapsByPrefix("image_preview:" + path)；若保留 mtime，则在缓存插入前先删除同路径旧前缀。

3. 其余问题

P2：析构时 ghost 用 deleteLater

ListView::~ListView()（ListView.cpp:747-752）对 m_ghosts 的 QLabel 用 deleteLater()。若实例在事件循环关闭后销毁，deleteLater 事件不会处理，幽灵残留。ListView 为进程级单例（生命周期≈进程），实际影响小；但未来若支持实例重建应改 delete。

P3：文件系统事件无节流

onFileSystemChanged（ListView_Actions.cpp:1127）每个事件直接同步处理，非自动排列时执行 loadIconLayer() 全量重建 + update()（:1140-1147）。批量复制 / 网盘同步 / 截图工具高频写入时会连续全量重建。

建议：LinDirectoryMonitor 侧或 ListView 侧加事件合并窗口（如 100-150ms 内的事件合并为一次刷新），或对 loadIconLayer 改增量更新。

P4：文件夹图标 matte 净化未缓存

DesktopRootItemState.cpp:322-329 的 sanitizeFolderPreviewMatte 对已缓存 pixmap 每次构建 renderData 都执行。renderData 在位置 / hover / 选择变化时重建，会反复净化。建议按 iconKey|matte|{side} 缓存净化结果（该函数为纯函数，输入相同输出相同）。

P5：乱码注释残留

ListView.cpp（构造段 318-329、358-370 等多处）与 ListView_Actions.cpp（1129、1139、1149 等）存在 GBK 乱码注释，此前统一 UTF-8 编码时遗漏。仅影响维护，不影响编译与功能。

5. 验证方式

  • 缓存上限：单元测试注入大量 key 断言条目数封顶；运行时在调试面板或日志输出缓存条目数。
  • 删除失效：删除桌面文件后断言 IconCacheManager 对应前缀条目减少（可在 clear() / invalidate 处打日志）。
  • 内存回归：任务管理器观察：反复增删 200 个文件 + 修改图片后，进程内存应稳定（不再单调爬升）。
  • 性能回归：批量复制 50 文件期间 UI 帧率稳定；onFileSystemChanged 日志中合并窗口内只触发 1-2 次刷新。

确认无问题的部分（无需改动）：构造初始化列表引用绑定顺序正确；monitor/timer/controller/viewModel 全部 parent this；BoxManager 用 QPointer 且 destroyBox 正确 deleteLater + 双索引移除；后台选择候选容器 begin/end/update 均 reset；renderData 内 QPixmap 随 state 析构释放。
