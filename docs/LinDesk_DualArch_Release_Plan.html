LinDesk 双架构（x86 + x64）发布改造方案

目标版本链路：1.1.2 · 发布仓库：linuup/LinDesk_Update · 执行人：anti · 2026-10-14

一句话目标：同一版本同时产出 x64 与 x86 两个安装包并发布到 GitHub Releases，更新器按用户机器位数拉取对应安装包，组件系统（CEF OSR）在两个架构下功能完整（方案 A）。

1. 背景与现状

需求：32 位与 64 位都要发布。经代码核对，现状存在 4 个必须解决的问题：

环节现状问题
构建 只有 build/build_64（-A x64 + Qt 5.15.2 msvc2019_64） 没有 32 位构建目录
Qt 部署 没有任何 windeployqt / DLL 拷贝步骤，Release 目录里的 Qt DLL 靠手动残留 根因：当前 build_64/Release 里的 Qt5*.dll 全是 x86（32 位），而 exe 是 x64，安装包把它们原样带出，导致干净机器启动报 QPlainTextEdit::dragEnterEvent 入口点错误
CEF 3rdparty/cef 仅一份 x64（libcef.dll = 0x8664，Chromium 154.0.8037.98） 32 位构建无法链接 x64 CEF 库
更新器 UpdateChecker.cpp 调 GitHub API，取 release 资产里第一个 LinDesk_Setup_*.exe 同一 release 放两个安装包时，客户端没有架构概念，可能拿错包

2. 目标产物布局

构建目录：
  build/build_64/Release/   → 64 位产物（exe + 64 位 Qt + CEF x64）
  build/build_32/Release/   → 32 位产物（exe + 32 位 Qt + CEF x86）

安装包（同一 tag vX.Y.Z 下的两个资产）：
  installer/LinDesk_Setup_X.Y.Z_x64.exe
  installer/LinDesk_Setup_X.Y.Z_x86.exe

发布记录：
  installer/update.json        （x64，主程序更新走 GitHub API，此文件仅作发布记录/手动安装）
  installer/update_x86.json    （x86 记录）

3. 分阶段改造方案

3.0 前置：下载 CEF win32（方案 A 核心）

CEF 官方提供 Windows 32-bit minimal distribution。从 CEF 自动构建镜像下载与现有同版本的 win32 包：

当前 x64 版本：Chromium 154.0.8037.98（见 3rdparty/cef/README.txt 第 10 行）
下载：cef_binary_154.0.8037.98+…_windows32.tar.bz2
解压到：3rdparty/cef32/   （目录结构应与 3rdparty/cef 一致：
                            include/ Release/ Debug/ Resources/ libcef_dll_wrapper/）
  • CEF 官方 CMake 支持 Windows 32-bit distribution（3rdparty/cef/CMakeLists.txt:99 有对应注释），目录结构与 x64 版一致，现有 CMake 逻辑可直接复用。
  • 解压后需保留 libcef_dll_wrapper 的 Release/ 与 Debug/ 两个 lib（CMakeLists 按配置引用）。

3.1 构建层：CMakeLists.txt 适配 + 新建 build_32

三处改动：

位置现状改为
CMakeLists.txt:90-95 if(WIN32 AND (…x64…)) → PREPEND CMAKE_PREFIX_PATH msvc2019_64，32 位时不设 Qt 路径 加对称的 else() 分支：32 位构建时 PREPEND F:/Qt/5.15.2/msvc2019
CMakeLists.txt:163 set(CEF_ROOT ".../3rdparty/cef" CACHE PATH …) 保持 CACHE PATH 参数化；32 位构建 configure 时传 -DCEF_ROOT=…/3rdparty/cef32（无需改 CMake 逻辑，:169 的 if(EXISTS include/cef_app.h) 自动生效）
CMakeLists.txt:207 LinWidgetRuntime include 硬编码 vcpkg_installed/x64-windows/include 按架构选择：x64 → x64-windows，x86 → x86-windows（vcpkg manifest 模式在 32 位构建会自动装 x86-windows 三元组，但 include 路径要跟着变）

新建 32 位构建目录（首次 configure）：

cmake -S D:/Desktop/LinDesk -B D:/Desktop/LinDesk/build/build_32 ^
      -G "Visual Studio 17 2022" -A Win32 ^
      -DBUILD_TESTING=OFF ^
      -DCEF_ROOT=D:/Desktop/LinDesk/3rdparty/cef32

首次 32 位构建前，vcpkg 需安装 x86-windows 三元组的 wil / gtest / spdlog（manifest 会在 configure 时自动处理，若未自动则手动 vcpkg install --triplet x86-windows）。

3.2 Qt 运行时部署层（补齐缺失的关键步骤）

每个架构构建完成后，用对应架构的 windeployqt 部署，部署前先清空该 Release 目录里旧的 Qt*.dll 与 plugins/（防止跨架构残留混装——这是当前 x86 DLL 混入 x64 目录的直接原因）：

# 64 位
del /q build\build_64\Release\Qt*.dll  &  rmdir /s /q build\build_64\Release\plugins
F:/Qt/5.15.2/msvc2019_64/bin/windeployqt.exe --release --no-translations build\build_64\Release\LinDesk.exe

# 32 位
del /q build\build_32\Release\Qt*.dll  &  rmdir /s /q build\build_32\Release\plugins
F:/Qt/5.15.2/msvc2019/bin/windeployqt.exe --release --no-translations build\build_32\Release\LinDesk.exe

windeployqt 会自动生成 plugins/platforms/qwindows.dll 及 imageformats、styles 等插件——当前 Release 目录 plugins/ 是空的，这一步必须补齐，否则新机器会报"无法加载 Qt 平台插件"。

OpenSSL：Qt5Network.dll 对 OpenSSL 是运行时动态加载（静态导入表只有系统 DLL，无 libssl/libcrypto），缺 DLL 程序仍能启动、仅 HTTPS/TLS 请求失败；且 windeployqt 不会部署 OpenSSL（Qt 的 bin 目录没有此文件，当前 Release 里的两个是手动放的）。两条路线：

  • 随包带 OpenSSL（现状，推荐先维持）：手动放 OpenSSL 1.1 x64 版 libssl-1_1-x64.dll + libcrypto-1_1-x64.dll（build_64/Release 已有）；x86 构建需补 32 位版 libssl-1_1.dll + libcrypto-1_1.dll（不带 -x64 后缀）。注意 OpenSSL 1.1.1 已于 2023-09 停止安全维护（EOL）。
  • 免 DLL（可选优化）：设置 QT_SSL_BACKEND=schannel 走 Windows 原生 TLS，不需要任何 OpenSSL DLL，同时避开 EOL 风险；切换前需验证证书校验 / pinning 行为在 schannel 后端下正常。

3.3 打包层：package.iss 架构参数化

要点说明
架构宏#define MyArch（x64 / x86），输出名 LinDesk_Setup_{#AppVersion}_{#MyArch}.exe
BuildDir按架构：x64 → build/build_64/Release，x86 → build/build_32/Release（当前 package.iss:4 硬编码 x64 路径）
64 位模式x64 版加 ArchitecturesAllowed=x64compatible 与 ArchitecturesInstallIn64BitMode=x64compatible（装到 Program Files）；x86 版不加（自动装 Program Files (x86)，{autopf} 已按架构解析）
VC 运行库package.iss:59 按架构选 vc_redist.x64.exe / vc_redist.x86.exe（x86 版运行库需放入打包源目录，目前只有 x64 版）
VC 检测注册表IsVCRuntimeInstalled()（:87-96）按架构：x64 → …\VC\Runtimes\x64；x86 → HKLM\SOFTWARE\WOW6432Node\Microsoft\VisualStudio\14.0\VC\Runtimes\x86

打包命令：

ISCC.exe installer\package.iss /DMyArch=x64 /DMyVersion=1.1.2
ISCC.exe installer\package.iss /DMyArch=x86 /DMyVersion=1.1.2

3.4 发布层：publish_release.py 双架构

现有脚本（scripts/publish_release.py）已支持 REST API 推送（api_publish_release）、模式 5 仅推送。改造点：

  • build_release() 已按 build_dir 参数化 —— 增加架构参数：x64 用 build/build_64（-A x64），x86 用 build/build_32（-A Win32 + -DCEF_ROOT=…/cef32）。
  • 构建/部署/打包按架构循环两次（版本号、翻译只做一次；同一 tag 上传两个 exe 资产 + 两个 update.json 资产）。
  • 资产命名：LinDesk_Setup_{version}_x64.exe、LinDesk_Setup_{version}_x86.exe。
  • SHA-256 分别计算写入对应 update.json（update.json = x64 记录，update_x86.json = x86 记录）。
  • 新增交互选项：--arch x64|x86|both（默认 both）；模式 5（仅推送）需允许指定架构或自动发现 _x64/_x86 包。

3.5 更新器层：按架构匹配资产

客户端必须按自身位数挑安装包，否则 64 位机可能拿到 32 位包（或反之）：

文件改动
src/services/update/UpdateChecker.cpp:148-159 资产匹配由"第一个 LinDesk_Setup_*.exe"改为按进程位数精确匹配：#ifdef _WIN64 时匹配 LinDesk_Setup_{ver}_x64.exe，否则匹配 _x86.exe；匹配不到则报错而不是取错包
src/services/update/UpdateDownloader.cpp:195-199 本地目标文件名 LinDesk_Setup_%1.exe 改为带架构后缀 LinDesk_Setup_%1_%2.exe（%2 = 架构），避免同名文件在下载缓存目录混淆（安装目录本身按位数不同，但文件名清晰更好排查）

位数判定用编译期宏 _WIN64（最可靠，与 exe 编译位数严格一致），不要用运行时 CPU 型号判断。

5. 验证清单

  • 位数自检：构建后遍历 Release/*.exe、Qt*.dll、plugins/**/*.dll、runtime/linwidget/*.dll 及 OpenSSL DLL，PE Machine 必须与目标架构一致（脚本化检查，写入发布脚本防回归）。
  • 全新安装：x64 机装 _x64.exe → 启动正常、组件系统可用；x86 机装 _x86.exe → 启动正常、组件系统可用。
  • 更新流程：旧版本（1.1.1 及更早）机器收到新版本提示 → 下载对应架构包 → 静默更新完成 → 启动正常（重点验证 dragEnterEvent 报错消失）。
  • TLS 可用性：随包带 OpenSSL 时验证 HTTPS 更新检查 / 下载正常；若切换 QT_SSL_BACKEND=schannel，验证证书校验与 pinning 行为一致。
  • 组件功能：两个架构下各加载一个小组件（时钟/壁纸），确认 CEF OSR 渲染、消息桥、拖拽正常。
  • 数据兼容：更新前后桌面图标 / box / map box 持久化数据不丢失（架构不影响 data.json 等用户数据文件）。
  • 回归检查：确认 Release 目录不再混入跨架构 Qt DLL；安装包内无 plugins 缺失。

6. 风险与注意事项

CEF 体积与维护成本：cef32 源码包约数百 MB，仓库将维护 3rdparty/cef（x64）与 3rdparty/cef32（x86）两份二进制。后续升级 CEF 版本时必须同步升级两个架构，否则 API 漂移会导致其中一个架构编译失败。

vcpkg x86 依赖：vcpkg.json（wil / gtest / spdlog）在 32 位构建需要 x86-windows 三元组，首次 configure 会自动安装；CI / 新机器配置前确认 vcpkg 可用。

旧安装包处置：当前 installer/ 下的 1.0.x ~ 1.1.2 包存在 Qt DLL 位数错配（x86 DLL + x64 exe），不应再作为"最新版"推送。发布 1.1.2 双架构包后，更新器自然会把用户带到正确的新包；旧包保留作回滚即可，无需删除。
